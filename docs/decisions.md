# Decisions

Log of design decisions. Settled ones record why; open ones record what decides them. Add an entry whenever a choice would be hard to reverse.

## Settled

D1. Local FreeSurfer directories are a first-class source. The census is one use of the package, not its only one. Consequence: everything downstream of `Source` sees local paths only; `surfcensus review PATH` must work offline in one command.

D2. Default renderer is pure Python (nibabel + matplotlib), Freeview is optional. Reason: headless, deterministic, no FreeSurfer license, parallel. Freeview stays for figures and as a cross-check.

D3. Three planes around the occipital pole, ping-pong, with frame-level scrubbing. Reason: Tomas's specification; scrubbing because experienced raters work frame by frame.

D4. Cortical thickness is the quantitative anchor, scored per vertex in fsaverage space (fsaverage6 default) against a per-vertex reference distribution. Parcel means are kept as a cheap baseline. Reason: the failure is local, and normal thickness varies over short distances in occipital cortex, so only a location-matched reference can say what is abnormal; fsaverage also puts rater marks and metrics on the same vertices. Supersedes the earlier plan of per-subject direction-of-normal ROIs, which remain only as an optional cross-check.

D8. Raters mark errors by clicking, and marks are resolved to native and fsaverage6 vertices. Required for positive ratings in census mode, optional locally. Reason: turns per-subject ratings into spatial ground truth, which enables census error maps, vertex-level detection analysis, and a test of whether the metric flags the right place.

D10. Datasets are shown by pseudonym by default, in the app, gallery, figures, tables and released data. Reason: to keep goodwill with the labs that shared data; the paper's point is about practice in the field, not about individual groups. Implementation:

- The pseudonym is a keyed hash: the first 8 hex characters of HMAC-SHA256(key, "<source>:<accession>"), prefixed `D-` (e.g. `D-3f9a1c07`). A plain unkeyed hash would be worthless: OpenNeuro accessions are a small enumerable set, so anyone could hash all of them and invert the mapping in seconds.
- The key is 32 random bytes generated by `surfcensus key init`, stored outside the run directory and outside version control (default `~/.config/surfcensus/dataset.key`, path configurable). Run directories record only the key's fingerprint (SHA-256 of the key, first 12 hex), so outputs made with different keys cannot be mixed by accident.
- The catalog stores accessions (it must, to fetch data), but no exported artefact does. `surfcensus export` writes pseudonyms only; `surfcensus export --reveal` writes the mapping table and requires the key. Collisions among 8-hex pseudonyms are checked at discovery and resolved by lengthening the affected pseudonyms.
- Reviewers or editors who need the mapping get it confidentially.

What pseudonymization does not do: it is goodwill, not secrecy. Per-dataset subject counts, field strength, age ranges and the renders themselves are derived from public data and can, with effort, be matched to OpenNeuro metadata. Released per-dataset tables therefore report coarse descriptors (field strength, subject count binned) rather than exact acquisition details. The paper should state plainly that identities are withheld as a courtesy, not hidden.

D9. The per-vertex reference is built twice: first from all subjects, then from rater-passed subjects. Reason: common failures contaminate the reference exactly where they occur; reporting both measures that cost.

D5. OpenNeuroDerivatives and embedded derivatives are analysed separately. Reason: one pipeline versus heterogeneous pipelines answer different questions.

D6. Raters are blind to dataset, scores and other ratings during rating. Local mode may sort by score unless `--blind`.

D7. The frontend has no build step. Reason: pip-installable without Node; easy to maintain.

D11 (2026-11-12). Render output is per-panel slice tiles in two layers, composed in the browser: a lossy grayscale WebP of the T1 slice and a lossless RGBA WebP of the contours. The browser stacks the layers, places the three panels, draws crosshairs and orientation letters, and plays both playback modes from frame tables in `render.json`. `anim.mp4` and `poster.webp` remain composite three-panel strips. Reason: lossy WebP at quality 80 desaturates thin coloured lines (mean absolute error 47, 16, 70 of 255 on contour pixels, measured on `ds000102` sub-01); composite strips cost about 10 MB per subject against about 4 MB for layered tiles (estimate from 15 sagittal tiles, one hemisphere); a separate contour layer lets raters hide the contours to see the tissue under the line; and one pixel-to-voxel affine per panel replaces one per frame. Supersedes the composite-strip frames first described in `rendering.md`. Consequence for the protocol: raters can toggle contours, which the pilot should take into account when timing ratings.

D12 (2026-11-12). The occipital box is anchored on the geometric pole (most posterior pial vertex per hemisphere). From milestone 3 the renderer also maps a fixed fsaverage pole vertex to native space through `sphere.reg` and records its distance to the geometric pole in `render.json`. The pilot decides from those distances whether the anchor should change. Reason: the geometric pole needs no template, so single-subject rendering stays self-contained, but it depends on head pitch and on the pial surface being correct at the pole.

D13 (2026-11-12). Panels follow Freeview's default 2D display orientation, with orientation letters on the panel edges, so the phase 0 comparison with Freeview is like for like. Implemented as two config switches (`radiological`, default true: subject's left on the right of the coronal and axial panels; `sagittal_anterior_left`, default false: posterior at the left). `render.json` records the orientation used. The defaults were first set from memory, with anterior at the left of the sagittal panel; reading Freeview's source the same day corrected that. In `RenderView2D.cpp` (dev branch; the sagittal and radiological cases are the same in v6.0.0 and v7.1.1) the sagittal camera sits at +x with view-up +z, which puts anterior at the right; the coronal camera sits at +y and the axial camera at −z with view-up +y, which is radiological with anterior up. A published Freeview screenshot shows the same edge labels. A neurological view exists only as an option (`-neuro-view`, from 7.4.0). The by-eye comparison of milestone 1 remains the check on a rendered frame.

D14 (2026-11-12). The fsaverage6 template (spheres, cortex label, search-region labels) is looked up in this order: a local FreeSurfer install, an `fsaverage/` directory next to the subjects, then a copy bundled in the wheel (about 1 to 2 MB). Reason: D1 requires `surfcensus review` to work offline, which fetch-on-first-use does not. Condition: bundling goes ahead only after Tomas confirms that the FreeSurfer licence permits redistributing these fsaverage-derived files (nilearn and TemplateFlow do so; the terms have not been read for this project).

D15 (2026-11-12; refined the same day in the review of milestone 1). Vertex-level spatial detectability is evaluated, per subject, only on search-region vertices that the subject's tiles show: the vertices with `visible` true in `vertex_map.npz`, whose pial position lies in the clickable region of `rendering.md`. Reason: raters can only mark what a tile shows, so search-region vertices that no tile shows would count as negatives that nobody inspected. `visible` is a property of the vertex's position, not of marks: a mark can resolve to a vertex that is not visible and still counts (`analysis_plan.md`, and D19, verification of the review fixes). The first wording was "inside that subject's rendered box (the vertices in `vertex_map.npz`)". It treated three sets as one: the box, what the tiles show (10 mm more than the box in x and z and 13.5 mm more in y with the default config), and the contents of the file, which now also holds a margin of vertices beyond what is shown, so that marks near a tile edge resolve to the right vertex. On `ds000102` sub-01 the box holds 31,548 pial vertices, 55,534 are visible, and the file holds 74,654. The parcel-based search region is kept for scoring.

D16 (2026-11-12). When no shipped reference applies and the local set has fewer than 30 subjects, no z-maps are computed; subjects are ranked on the raw ceiling fraction and the raw occipital-to-control regional thickness ratio, and the output says so. Reason: a per-vertex median and MAD from a handful of subjects is not meaningful. Whether to ship a provisional reference built from unrated census subjects stays open under O7.

D17 (2026-11-12). The code is licensed BSD-3-Clause. The licence for released ratings stays open under O12.

D18 (2026-11-12). Working conventions. Geometry is in mm throughout, so volumes that are not 1 mm conformed are handled. The T1 is upsampled by nearest neighbour, as in Freeview. "Deterministic" (hard rule in `CLAUDE.md`) means for a given input, config and locked environment (`uv.lock`); golden tests use a tolerance. The catalog uses stdlib `sqlite3` with `PRAGMA user_version` migrations, and `sqlmodel` stays in the `app` extra. The version stays static until the first tagged release. Regional metrics, ceiling fraction and scoring are built in milestone 3 because `review` orders its queue by the composite score; the intensity metric follows milestone 4. CI runs lint and tests on Linux and macOS for Python 3.11 and 3.13.

D19 (2026-11-12). Choices made while building milestone 1, with their reasons.

- Orientation check. nibabel's vox2ras-tkr ignores the direction cosines, so the documented test (tkr matrix not a signed permutation) could never fail on a file. The renderer refuses a volume whose scanner affine and tkr affine differ in their linear part, that is, any volume not in conformed LIA orientation.
- Contours are joined into polylines before drawing (see `rendering.md`); `LineCollection` of separate segments gave unevenly heavy lines.
- The video setting is part of a render's identity: asking for a render without video in a directory that has one renders again and removes the video.
- `vertex_map.npz` is stored uncompressed with fixed entry dates, for byte identity across zlib builds (1.8 MB instead of about 1.3 MB on one subject; with the selection rule of the coordinates review below, 2.5 MB instead of 1.7 MB from `numpy.savez_compressed`).
- The video is converted with the BT.709 matrix, limited range, and tagged, so players need not guess; swscale's bit-exact path is forced because its SIMD path gave different bytes.
- `three_plane(subject, "x.mp4")` renders into a hidden temporary directory next to the target and moves the video into place.
- `render.json` records an input only under a name that FreeSurfer gives a file of that role. A link to a pial variant in the same directory (`lh.pial -> lh.pial.T1`, FreeSurfer 7) is recorded under the variant's name. A link to anything else, in the same or in another directory, is recorded under the link's own name, and a file handed to `render_subject` under a name that is not the role's (a download cache may do that) under the role's first name. So no foreign name reaches `render.json`. Before the review a link such as `T1.mgz -> ds000999_sub-01_T1.mgz` in the same directory put the target's name into `render.json`.
- A directory is treated as an fsaverage template if its own name or the name of its link target starts with `fsaverage`.
- Tests run the package under jaxtyping and beartype with the PEP 484 numeric tower (an `int` passes where `float` is annotated), in agreement with the static checker.
- Byte identity of renders was checked on one machine across Python 3.11 (numpy 2.4) and 3.13 (numpy 2.5): identical media bytes. Not checked across machines or operating systems.

Added in the review of milestone 1 (robustness, 2026-11-12):

- Renders into one media directory are serialized by `flock` on the directory itself. Chosen over a lock file: it leaves nothing in the directory that the completeness check, the cleanup or the list of a render's files would have to know about, and the kernel releases it when the process dies, so a killed render cannot leave the directory locked. A lock file made with `O_EXCL` would be portable, but it stays behind after a kill and then needs a rule for when it is stale. Where `flock` is missing (Windows) or refused, the render runs without a lock, as it did before. Measurements and what was not checked (macOS, NFS) are in `rendering.md`.
- Cleanup removes files by the names a render writes, not by glob over the directory: a user's `.notes.tmp` or `tiles/mine.webp` in the output directory used to be deleted. Temporary files are removed only under the lock. This review still removed any `anim.mp4` in a render without video and did not refuse the subject directory as output; both were changed when the fixes were verified (below).
- `RenderConfig` checks colours (`#RRGGBB`) and bounds `line_width_px` by `panel_px / 8`, and `render_subject` validates the config again, since `model_copy(update=...)` skips validation. Before, a bad colour or a very wide line failed while drawing, after `render.json` of a complete render had been removed. The bound of an eighth is a choice: 40 px at the default panel, 2 px at the smallest (16 px), where the default line of 1.25 px still passes.
- Absent and unreadable are told apart by the package's own `stat()` probe (`sources/patterns.py`), not by `Path.is_file()`: for a file in a directory without search permission, `is_file()` raises `PermissionError` on Python 3.11.18 and 3.13.18 and returns False on 3.14.6 (run 2026-11-12 on Linux without `CAP_DAC_OVERRIDE`). `resolve_subject_files` and `is_freesurfer_subject_dir` raise `OSError` for a path they cannot examine, and the renderer turns that into `render failure`. They do not answer "absent" or "not a subject", because a scan would then drop an unreadable subject without a trace. The scan of milestone 2 has to catch the error for each directory and record it as unreadable. A name too long for the file system counts as absent.
- With a video target, `three_plane` does every check before it creates the parent directory or the temporary directory, and removes the directories it created if the render fails afterwards. The command line handles SIGTERM like Ctrl-C; a render killed with SIGKILL still leaves its hidden temporary directory next to the target.

Added in the review of milestone 1 (determinism, 2026-11-12):

- The contour renderer resets `path.sketch` on its artists, so a `matplotlibrc` or an earlier `plt.xkcd()` cannot change a tile. Chosen over drawing inside `matplotlib.rc_context` with default settings: that would change global state for the length of a draw, which is not safe with two threads rendering in one process, and the review's sweep of all rcParams found no other setting that reaches the tile. Measurements are in `rendering.md`.
- Config colours have one validation, a field validator that requires `#RRGGBB` and stores the upper-case form; it replaces the pattern check added in the robustness review. Lower-case colours used to give another config hash for the same bytes, so a change of letter case in a run config would have rendered every subject again. The hash of the default config did not change (`dff40fe66869`): the defaults were already upper case, and a validation rule is not part of the hashed payload. A test pins that value, since it may change only when the serialized value of a default or the schema version changes.
- `vox2pix` is the inverse of `pix2vox` in closed form, with negative zeros removed from both matrices. `np.linalg.inv` gave the last bit of the shifts and a `-0.0` of the LAPACK that numpy is linked with, which `uv.lock` does not pin (the review notes OpenBLAS in the Linux wheel and Accelerate in the macOS arm64 wheel, and reproduced other digits with reference LAPACK 3.12 on Linux). Checked on this machine on 10 renders before and after the change (synthetic subjects at 1, 0.8 and 0.7 mm and `ds000102` sub-01, panels of 64 to 384 px, both display orientations): every tile, poster, video and vertex map is byte-identical, and `render.json` differs only in `vox2pix`: `-0.0` became `0.0` in every render (one entry in the axial panel, four entries with the flipped orientations), and the last digit of a shift changed in 3 of the 10 (0.8 mm at the default panel, sub-01 at 384 px and at 334 px; for example `-160.0` became `-160.00000000000003`, the value the review got from reference LAPACK). Not removed: contour coordinates still pass through `np.linalg.inv` of the vox2ras-tkr affine (`geometry.tkr_to_pixel`), so tile bytes could in principle depend on LAPACK in the last bit of a coordinate. The review rendered three subjects with reference LAPACK and found all media files identical. Not checked on macOS.
- When the video is asked for, the ffmpeg binary is looked up before the volume and the surfaces are loaded and before anything is written, and a missing one is a `RenderError` with reason `render failure`. Before, `IMAGEIO_FFMPEG_EXE` pointing at a missing file surfaced as `FileNotFoundError` after `render.json` of a complete render had been removed and all tiles written again. The reason is one of the protocol's unratable reasons, although the cause lies in the environment and not in the subject: the census render phase (milestone 5) must not record it as a property of the subject. `write_mp4` now raises `RuntimeError`, as its documentation says, also for a binary that cannot be started and for one that exits with status 0 without a video. Both used to raise `OSError`, and a binary that exited with status 0 and left an empty file would have replaced an existing `anim.mp4` with it.
- The command-line tests do not depend on the terminal. Typer hands usage errors and help pages to Rich and forces Rich's terminal output when `GITHUB_ACTIONS`, `FORCE_COLOR` or `PY_COLORS` is set; Rich then puts escape codes inside option names (`--no-video` in three pieces), and it wraps to the terminal width. At the reviewed commit that failed `test_no_video_contradicts_a_video_path`, in every cell of the CI matrix according to the review; the test of an empty `--out` added in the robustness review failed the same way (run here with `GITHUB_ACTIONS=true` and `FORCE_COLOR=1` before the change: 3 failed, 9 passed in `tests/test_cli_render.py`). The tests now read the output with escape codes and frame removed and white space collapsed, and each test that reads such output runs three times (plain, forced colour at 80 columns, forced colour at 30 columns) with the variables Rich reads set by the fixture, so the CI condition is tested in every environment. Not chosen: disabling Rich for the tests (`_TYPER_FORCE_DISABLE_TERMINAL`), which would leave the output users get on CI untested.

Added in the review of milestone 1 (coordinates, 2026-11-12):

- `vertex_map.npz` is selected by what the tiles show, not by the view box, and D15 is refined accordingly. The rule, the measurements on `ds000102` sub-01 and the cost (1.8 to 2.5 MB for the file, 10.2 to 10.9 MB of media per subject) are in `rendering.md`.
- The region is the union of the three panels' boxes, not the cube of the field of view. The cube is simpler and nearly the same size (with a 5 mm margin 75,435 vertices on sub-01 against 74,654), but its eight corner blocks are shown by no tile: they lie outside the slice range of all three panels. 602 pial vertices of sub-01 lie there, and `visible` must be false for them, or D15 would count them as inspected.
- The region is grown box by box along the axes, not by Euclidean distance. That keeps a few vertices near the edges and corners of the grown boxes that no mark can reach, and it lets a reader recompute the selection from `render.json` with comparisons alone.
- Half a slice step means half of `slice_step_mm`, also where the slice planes are farther apart or closer than the step because the voxels are not the size of the step. It matters only at the two ends of each panel's sweep.
- `vertex_map_margin_mm` keeps its name and changes its meaning: the margin beyond the clickable region (default 5 mm, the snap radius) instead of the margin beyond the box (default 10 mm). The file gained arrays and `render.json` gained the counts of visible vertices, so the render schema version went from 1 to 2. The version is part of every config hash, so a render made under the old meaning cannot pass for an up-to-date render of a config that sets the margin to 10, which would otherwise hash like the old default. (The new counts are required fields, so an old `render.json` also fails to load; the version says why.) The hash of the default config changed from `dff40fe66869` to `17f83a0c9b6c`, and the test that pins it was updated. Every existing render is rendered again on the next request; a test does that with a render.json and vertex map in the form of version 1.
- `vertexmap.build_vertex_map` takes the region as an array of boxes instead of the view box, and `read_vertex_map` returns the `visible` arrays with the rest.
- `visible` is defined on the pial position alone. A vertex whose white position is shown and whose pial position is not is in the file and is not visible. D15 concerns pial capture; if white-surface marks (class C) get their own spatial analysis, it needs its own flag.
- Not done here: the app (milestone 4) has to refuse a snap radius larger than the `vertex_map_margin_mm` of the render it serves. Measured on one real subject (FreeSurfer 6.0.1, 1 mm) and on synthetic subjects at 1 and 0.8 mm; no FreeSurfer 7 subject.

Added in the review of milestone 1 (tests and docs, 2026-11-12):

- The review ran the tests against copies of the package with one thing broken in each, and found broken copies that passed all of them. Eleven tests (eighteen cases) were added and four existing ones tightened, so that each of these now fails at least one; the package code did not change for them. The broken copies: only the first, or only the first two, closed loops of a surface drawn on a tile; the crosshair of frame 0 on every frame of video and poster, or on the poster alone, the crosshair at another coronal slice, and no edge letters; an orientation tolerance of 5e-2, 1e-3 or 1e-5 in place of 1e-4; in `render.json`, a voxel size of 1 mm for every volume, two dimensions of the shape exchanged, and the left pole's vertex number for the right pole; an exact half in the synchronized frame table rounded up or down; the sagittal panel half a pixel off when `sagittal_anterior_left` is set; the video with the BT.601 matrix, without `-threads 1`, with preset `ultrafast`, or without `-flags:v +bitexact`; an input hashed over its first MiB only; an input name that may be a path; a NaN voxel that reaches the cast to `uint8`.
- The folded test mesh is a closed surface, a sphere whose radius is modulated into six gyri, which a sagittal plane crosses in three loops. `architecture.md` had planned a folded slab; the surface does the same job with a mesh the tests already build. Every other synthetic surface is an ellipsoid and gives one loop per tile.
- The network test compares the line coverage of every contour tile with the length of the contours on the tile times the line width, computed from the slicer. Measured on `ds000102` sub-01: 0.952 to 1.005 per tile, 0.976 over all tiles; on 152 of the 155 tiles with contours a surface gives more than one line, 15 at most. With only the first closed loop of each surface drawn the same ratios are 0.37 for the worst tile and 0.88 over all tiles, and the test as it was before (more than 80 % of tiles have some contour) passed. The test also checks size and SHA-256 of the six inputs, which are 1.7 to 5.6 MB; no synthetic input was larger than 0.4 MB.
- The encoder settings are checked on the ffmpeg command line. Preset and bit-exact flags do not show in a file that is made and read back on one machine, so no test of the output can pin them. The thread count is tested by its effect as well: ffmpeg is shown one processor and then all of them (`os.sched_setaffinity`), and the two files must be identical. That test needs Linux and more than one processor and is skipped elsewhere, so in CI it runs in the Linux cells only.
- The orientation tolerance is tested on both sides: a scanner affine turned by 5e-5 rad is rendered, 2e-4 rad is refused. The render of the turned volume has the tiles, poster, video and vertex map of the unturned one, byte for byte; only `render.json` differs. Image and contours are both placed through vox2ras-tkr, which nibabel builds without the direction cosines, so the tolerance does not decide whether contours sit on the image. It decides how far the edge letters, the pole anchor and the box may be turned against the anatomy.
- The geometry tests had no case with `sagittal_anterior_left` set since D13 changed its default: the case named `posterior_left` was the default config. The cases now cover both switches both ways, and a test says so.
- `README.md` describes what is built (`render-subject` and `render.three_plane`) and lists `review`, `export` and the census as planned. It had shown only commands that do not exist.

Added in the final check of the milestone 1 review (2026-11-12):

- A damaged input is reported like one that may not be opened: `unreadable input (<file name>: <error>)`, with the file's path removed from the error text. Before, the text of nibabel's exception was passed on as it was, and for an empty `T1.mgz` or `brainmask.mgz` it holds the whole path (`Empty file: '/.../mri/T1.mgz'`), against the rule of the robustness review that the message names the file and not the path. Tried on a synthetic subject with a truncated, an empty and a garbage `T1.mgz`, a garbage brainmask, and a truncated, an empty and a garbage surface: only the two empty volumes carried a path.
- `RenderConfig` refuses a view box that no panel can show: a low end above the high end along an axis, or no extent along any axis together with a `margin_mm` of 0. Before, such a config was accepted and then refused once per subject as `render failure` ("the view box lies outside the volume", "no extent"), which a census would have recorded as a failure of every subject. A box that is flat along one or two axes is still allowed. The check in `geometry.field_of_view` stays for a config that was not validated.
- The four reviews together were checked on `ds000102` sub-01: all 352 tiles, `poster.webp` and `anim.mp4` are byte-identical to the render made before the review (schema 1); `vertex_map.npz` (2,465,892 bytes, 74,654 vertices) and `render.json` differ as described above; 10.9 MB of media in 356 files, rendered in 8.7 to 9.3 s on one core (three runs).

Added in the verification of the review fixes (2026-11-12). Independent checks of the fixes above found seven problems; what was done about each:

- `anim.mp4` belongs to a render only if the `render.json` in the directory lists a video. A render without video used to remove any `anim.mp4`, also in a directory that was never rendered into (`render-subject SUBJECT --out . --no-video` in a directory with a film of that name). The earlier `render.json` is read as plain JSON, so that a render of schema 1, which does not load under the present model, still gives up its video. The video is removed before `render.json`, not at the end of the render with the stale tiles: a render without video that is interrupted would otherwise leave the earlier video with no `render.json` to say whose it is. One such case remains: a render with video that is interrupted leaves an `anim.mp4`, the earlier one or its own, and a later render without video then leaves it in place, unlisted. Chosen over a marker file, which every other part of the cleanup would have to know.
- An output in a source directory is refused (`OutputInSourceError`, a `ValueError`; exit status 2 on the command line). The robustness review had left this to milestone 2. It is done now because the case that loses a file needs no run directory: `render-subject sub-01 --out sub-01 --no-video` removed an `anim.mp4` in the subject directory, and any render there adds files to a source, against the hard rule. The rule is applied in `render_subject`, which sees only files, so it works from where the files are: the subject directory for a file at its FreeSurfer place, else the directory that holds the file, and for a link the directory of its target. An output directory that holds the subject directory is accepted, since nothing in the subject directory changes; a `SUBJECTS_DIR` given as `--out` gets `tiles/` and `render.json` next to its subjects.
- The pattern for a render's tiles had `\d`, which in Python matches every Unicode decimal digit, and allowed any number of leading zeros. `tiles/axial_٠٠٠.webp` and `tiles/axial_0001.webp` were removed as stale tiles although the renderer cannot write either name. The pattern now has ASCII digits: three, or four and more without a leading zero.
- Cleanup removes files and links only. A directory under the name of a stale tile (`tiles/coronal_998.webp/`) made `unlink` raise `IsADirectoryError` after `render.json` was removed and every tile rewritten, in this render and in every later one. Not changed: a directory under a name that the render does write (`tiles/coronal_000.webp/`) still fails as an `OSError` when the tile is moved into place, like any output location that cannot be written.
- `visible` keeps its rule (the pial position lies in the clickable region), and the documents no longer say that it holds every vertex at which a drawn contour can appear. Measured on `ds000102` sub-01: 1,181 of 373,536 pixels of the drawn pial contour (0.32 %) resolve to a vertex that is not visible, at most 1.07 mm outside the region. The other rule was measured as well: with the corners of every pial face that a slice plane cuts inside the panel's field of view added, 57,484 vertices are visible instead of 55,534 and none of the 373,536 pixels resolves outside them. It was not adopted. A mark need not lie on the contour, since it snaps over up to 5 mm, so no rule for `visible` makes every mark's vertex visible, and the analysis has to say what it does with such a mark in either case (`analysis_plan.md`: the mark is kept, its own vertex is not counted). The region rule can be recomputed from `render.json` by comparisons, which a rule on cut faces cannot once the surfaces are deleted; a pial face of sub-01 is up to 7.5 mm long (median edge 0.95 mm), so its corners can lie well outside what is shown; and the flags of every existing render would change, which is another schema version. If the pilot shows marks at tile edges to matter, this is the place to change.
- Two tests did not fail when the thing they are named for was removed. The test for negative zeros had no case with a shift of zero; a case with a tile edge on voxel coordinate 0 was added (the default box around x = 88 in a conformed volume). The test of a schema 1 render used a `render.json` that does not load under the present model, so it was rendered again whatever the version logic did; it now also runs on files that load, with the version number of schema 1, with its config hash, and with both. Each new and each changed test of this round was run against a copy of the package with its fix undone, and fails there.
- `docs/dev/contract.md` was corrected where it described the working tree or the other documents wrongly.

D20 (2026-11-12). The privacy boundary of D10 is built into what code can reach, not left to convention. Implementation, milestone 2:

- Private values exist only in `catalog.sqlite` and are read only through `store.Catalog`, which `run.py`, `cli.py` and the inventory use: accessions, roots and identities, `dataset_id` (assigned in the order of the bucket listing), file locations, sizes, ETags and digests, input signatures, failure details, the run secret, and in a census run the subject labels. One exception, on disk only: the sizes and SHA-256 digests of the files a render read are also in `media/<subject_uid>/render.json` (`inputs`), because they tie the render to exact source bytes. They match the public bucket files, so `render.json` is never served or exported as a file; what leaves the run directory is the tiles, the poster and the video, and the app of milestone 4 passes the geometry without `inputs`. Code downstream of the inventory gets a `store.PublicCatalog`, which returns none of these, inside a `records.RunContext`; a phase function never receives the `Run`.
- No unkeyed hash of public bucket metadata leaves the catalog. An input signature is a plain hash of sizes and ETags, so it stays inside. What identifies a render elsewhere is `render_key`, an HMAC under a per-run secret of 32 random bytes (`meta.run_secret`) over the tile settings and the SHA-256 digests of the files read. Cache names are keyed the same way.
- `config.yaml` of a census run holds no path and no accession: a local source in it is stored by its pseudonym, and its root is in the catalog.
- The text of a failure that is recorded (a row, a report note, a log line) passes through `privacy.scrub` first: dataset roots, absolute paths, accessions and, in a census run, subject labels are taken out. A configuration error that stops a command is printed as it is, on the terminal of whoever ran it.
- Everything written or returned outside the catalog is ordered by pseudonym or `subject_uid`, never by `dataset_id`.

- A test reads the source of the downstream packages (`metrics/`, `render/`, `app/`, `export/`, `select/`, `reference/`, `calibration.py`; today only `render/` exists) and fails on an import of the private catalog, of `run.py` or of the reveal path, on an attribute named `_catalog`, and on the string literals `accession` and `dataset_id`.

Reason: a rule that every module must remember fails at the first module that forgets. Not yet built: the canary run on a fake bucket dataset, which needs the remote source of milestone 5, and the reveal path.

D21 (2026-11-12). One skip rule for every phase, decided from the listing. A unit is skipped when its row says `done`, its config hash and input signature are those of the present configuration and listing, and its output exists. A failed unit with the same hashes is not tried again unless `--retry-failed`; `--force` ignores the row. The input signature is computed from role, location, size and ETag or modification time, and for a role with several candidate names from the name that was read, so the decision opens no source file. Outputs are written before the row, so a crash never leaves a row without its output. Rows live in the `work` ledger (keyed by phase and unit) and, for renders, in `renders`. Reasons: a phase that is interrupted or run twice redoes nothing that is done, and a census can be resumed per dataset. Consequences worked out in milestone 2:

- The inventory has no ledger rows; its skip test is `subjects.inventory_hash`, the signature over all listed files with the inventory stage hash. Two cases add lines to that hash: a directory that could not be listed adds its problem text, and a subject whose build stamp, log or stats file could not be read gets a marker that no listing gives, so the next inventory reads it again. An unread Tier A file is not a failed unit. A dataset whose subjects cannot be listed is a failed unit `dataset:<pseudonym>`; its subjects are not marked absent, and the detail is in the report notes and the log only.
- Frames from the catalog and from `read_table` have fixed column types whatever the rows hold: text is `object` with None, a flag that may be unknown is pandas `boolean`, an integer that may be missing a pandas nullable integer. Parquet tables are sorted by their key and then by the remaining columns, and a NaN is written as a missing value, so the bytes of a table depend on its set of rows and the locked pyarrow only. Checked on Python 3.11 and 3.13 on one machine.
- `Catalog.mark_absent` sets `present` from the listing in both directions. `Catalog.relocate` refuses data of another pipeline, because the pipeline is hashed into `subject_uid`. When the data moved into a layout with another `fs_root`, it moves `subjects.fs_dir` of every subject of the dataset in the same transaction: the inventory skips a subject whose files are unchanged, and `inventory_hash` does not cover `fs_dir`, so no later phase would correct it. For the same reason the inventory's skip test compares the stored `fs_dir` beside the hash: subjects that moved, at the same root, into another layout of the same pipeline (`freesurfer/sub-01` to `sub-01`) are stored again and keep their `subject_uid`, renders and ratings. A dataset never changes its pseudonym: a different one for a stored dataset is treated as a wrong key.
- Data that is found in the layout of another pipeline at the same root (a subjects directory moved into `sourcedata/freesurfer/`, an fMRIPrep output written beside a `freesurfer/` folder, which the layout rules then prefer) is a second dataset row with the same pseudonym, and its subjects get new `subject_uid`s, because the pipeline is hashed into them. The subjects of the earlier row are no longer listed: the inventory marks them absent, sets the row's listed count to 0 and says so in a note, once the new listing has succeeded. Before this they stayed present and every subject counted twice. Their renders and ratings stay under the old identifiers and are not carried over. When the earlier pipeline was `freesurfer`, the earlier subjects come back with their renders by giving the directory that holds the subject directories as `--source` with `--relocate`, since such a directory is always read as a plain subjects directory (tried once, on a subjects directory moved into `sourcedata/freesurfer/`); there is no such way back to an earlier `fmriprep` row once the fMRIPrep layout is gone. `status` names a pseudonym once. `--relocate` moves the rows of the pipeline found at the new place and takes the root of an earlier row along.

Reason: under fMRIPrep the flags are spread over the invocations of three logs, of which the first 64 kB of `recon-all.log` show 2 of 4 (FreeSurfer 6.0.1) or 2 of 5 (7.3.2); the thickness truncation counts are in the per-hemisphere logs only; and the closing line is at the end. D29 (2026-11-12). Choices made while building milestone 2 (local source, config, catalog, inventory, `Run`, the `inventory`, `render` and `status` commands), with their reasons. The numbers D22 and D24 to D28 are held for decisions that land with milestones 3 to 5 (`docs/dev/contract.md`, section 10). Where a choice departs from that contract, it says so.

Decisions taken for this build, from the contract's list of questions for Tomas: no fsaverage-derived file ships in the wheel (the condition of D14 is not met); a local run renders without video unless `--video` (`render_video` is false in a new local run), since the rater app plays tiles and the video costs 2.5 of 9 s and 4.3 of 10.2 MB per subject; the embedded-derivatives source is deferred (O9).

Local source.

- A path that is not a directory is `SourceError("not found")`, one that cannot be listed is `unreadable`; `layout` means a readable directory without subjects. The contract named only `layout`.
- A subject glob that matches nothing is reported when the subjects are listed, not when the source is built, so a run whose stored glob no longer matches can still be opened. The command line checks a glob before it creates a run or stores the glob.
- One subject directory as path: the source is its parent restricted to that name. Globs given as well must match the name.
- A subject directory whose name is not valid UTF-8 (Latin-1 bytes, which Linux file systems take) is skipped with a warning. A label is hashed into the `subject_uid` and stored as text, and such a name can be neither; before, it stopped every inventory of its dataset with a `UnicodeEncodeError`. Renaming the directory is the way to include it. Tried on one Linux file system only.
- `field_strength` is positive and finite: `LocalSource` raises `ValueError` and `SourceConfig` refuses the value, also for infinity; the command line turns either into `invalid: ...` with exit code 2, on a new run as on a stored one.
- `template_location` is recorded when an `fsaverage` directory exists next to the subjects, also when it lacks template files, so the template lookup can name what is missing; `template_dir()` returns it only when all eight files are present. `template_files_missing()` and `LocalSource.subjects_dir` were added.
- A subject directory reached through a link keeps the link's name as its label. A folder named `fmriprep` next to `freesurfer/` is recognised by the name as given and by the name of what it links to.
- Paths are built from the source's own root, not from the root in a record, so a record from a catalog that still names an earlier place is served from where the data is. `FileRef.variant` is set only for roles with several candidate names; `render.json` names its inputs through the same function (`patterns.variant_name`), where the renderer had its own copy of the rule of D19 before the review. A local source ignores the `only` argument of `datasets()`.
- `read_bytes` raises `not found` for a role the subject lacks, `changed` for a file that is gone or differs from the listing, `unreadable` for one that cannot be opened; the detail holds the location relative to the subject, never an absolute path. Modification times are compared in nanoseconds. Run on one Linux file system only.

Provenance. The rules were fixed on the logs of two real subjects and on `scripts/recon-all` at v6.0.0 and v7.4.1 (`data_sources.md`); excerpts of the six logs, with directory names, accession and host replaced, are test data.

- Flag names: besides tokens of the form `-name`, `-3T` and `-3t` are kept (real flags, the only ones that start with a digit), and a flag-shaped token that contains an accession is dropped.
- T2pial, FLAIRpial and hires use the spellings that recon-all's argument parser takes (`-T2pial`, `-t2pial`, `-T2pial-only`, `-autorecon3-T2pial`; off: `-noT2pial`, `-no-T2pial`, `-no_T2pial` and the lower-case forms; likewise FLAIR; `-hires`, `-highres`). recon-all has no flag that clears `-hires`.
- `finished` is the verdict of the last invocation, not of the last verdict line in the file: a log whose last invocation was killed is not finished.
- A flag is stored as false only when the logs can show it (every log the subject has was read in full, and an invocation was found); otherwise an unseen flag is unknown. The contract had unknown only for "no log read".
- A bare carriage return ends a line (the logs hold progress output). Numbers in the patterns are bounded in length, because nothing in this module may raise on any text. With a partial text, a last line without a line end is ignored.
- The version comes from the build stamp file, else from the stamp line of `recon-all.log`, also when the file's stamp holds no version. Holes come from `recon-all.log`, else from a per-hemisphere log.
- The contract's statement that the 7.3.2 log does not separate invocations was wrong: it writes `#New# invocation of recon-all`.
- Not checked: a log of a plain `recon-all -all` run; which of the two truncation counts is white-to-pial; where `-T2pial` appears when a T2 was used; `-autorecon2-pial`, which is in neither version read and is kept as an edit flag from memory.

Catalog.

- Beside the methods of the contract, `Catalog` has `query`, `pseudonym` and `scrub_terms`, and the module has `media_dir`, `table_path`, `part_path` and a `schema` argument on the part functions (the intensity table of a run with other depths has its own schema).
- `upsert_dataset` keeps a stored derivative ref, snapshot tag and subject count when given None. `upsert_subject` takes the digests of the files that the inventory read in full (a keyword argument that the contract did not have) and writes them with the subject; a file that is not among them keeps its digest while its location, variant, size and ETag or modification time are unchanged. It stores `recon_flags` as NULL when no log was read, and raises `ConfigError("invalid")` on a collision of two subjects on one `subject_uid` and `ConfigError("key")` when a subject is stored under another one.
- `PublicCatalog.meta` raises for a key that is not public, so a request for the run secret is loud. `Catalog.set_meta` refuses to change what identifies the run.
- `Catalog.failures` also lists unreadable subjects (phase `inventory`) and failed renders (phase `render`).
- A migration is split into statements by line and run in one transaction; `executescript` would commit on its own.
- One connection per catalog, usable from several threads behind a lock (the rater app answers from a thread pool). Methods cannot be called inside an open `write()` block.
- A catalog that another connection keeps locked for longer than the busy timeout is reported as in use (`ConfigError("invalid", "catalog.sqlite is in use by another process; ...")`), on opening and at the start of a write. Before, opening reported it as "not a SQLite database", which invites deleting the catalog, the only copy of the run secret. The wait on opening is the 60 s of a census run also for a local run, because the mode is read from the file.
- When a write fails, the transaction is rolled back only if SQLite has not ended it already. On a full disk it has, and the rollback then raised "cannot rollback - no transaction is active" in place of "database or disk is full". Reproduced with `PRAGMA max_page_count` and on a 64 kB tmpfs.
- Not checked: write-ahead mode on a real network file system; the list of file system types treated as network mounts is from memory; the two-process write test ran on one local disk.

Batches.

- An exception comes back from a worker process as an instance of its own class. The package's error classes take `(reason, detail)`, and pickle could not read them back: a process pool that received one was broken for the whole batch (seen with `SourceError` on Python 3.13). `run_batches` carries exceptions as class, arguments and attributes, and `SourceError`, `ConfigError` and `RenderError` now also pickle on their own. An exception that cannot be sent arrives as `batches.WorkerError`.
- A subject whose worker process dies gets `BrokenProcessPool`; the subjects lost with it are run again one at a time, so a work function must be safe to repeat.
- Workers ignore SIGINT: on Ctrl-C the parent waits for running work, releases the leases and stops, and the interrupted batch is not committed.
- Log records of the package logger made in a worker are logged in the parent when the subject finishes, so a filter on the package logger sees them. The progress bar is drawn only when stderr is a terminal.
- A work function that cannot be pickled is a `TypeError` before anything is leased.

Inventory. See D21 for the hash. Also: a listed subject with a problem is a failed unit whether it was stored now or skipped, so a second run reports the same count; a pseudonym in `--dataset` that no source yields is a failed unit; two sources that yield the same dataset are refused; `field_strength` of a source is written to the listed subjects, also to skipped ones, so a changed `--field-strength` needs no `--force`. `dataset_files` is not written yet. Behaviour with a remote source is tested only with a local source posing as one.

Added in the review of milestone 2 (2026-11-12), two findings on what a stored subject traces back to:

- The name of the file that was read is part of the input signature (D21). A FreeSurfer 7 subject has `surf/lh.pial` as a link to `lh.pial.T1`, or to `lh.pial.T2` after a T2 refinement. The role's location is the link, the variants of one subject have the same size, and a copy that keeps the modification time (`cp -p`) has the same time, so a link pointed at another variant gave the same signature: the inventory skipped the subject and kept `pial_variant = pial.T1` and `t2pial = 0`, and the render of the subject was skipped as well, so its tiles stayed those of the other surface. Reproduced in tests on synthetic trees, for the inventory and for the render; it needs the equal modification time, so it is rare. The signature of every subject changes with this, since the pial roles always have a variant: a catalog made before it inventories every subject once more, and its renders are found complete on disk and recorded again without rendering. For the same reason `upsert_subject` drops a kept digest when the variant changed.
- The build stamp and the three logs get their SHA-256 in `files.sha256` when the inventory read them whole, as the files of a render do. Before, `recon_flags`, `n_invocations`, the holes and the truncation counts traced to a size and a modification time only, which for a local file do not say which bytes were parsed. A log of which only the head was read (`inventory.logs = "head"`) gets no digest, and keeps one from an earlier full reading while its listing is unchanged. The stats files are not read by the inventory and get none until the regional metrics of milestone 3 read them. The digests are written in the transaction that stores the subject; written after it, an interruption in between would leave a subject that every later inventory skips without them. Checked on the two real subjects of the network tests (`ds000102` sub-01, `ds003020` sub-UTS01), linked into a scratch subjects directory: the eight files have in the catalog the SHA-256 of their bytes, no other file has a digest, and a second inventory skips both subjects.

Rendering a run (`render/batch.py`).

- `run_render` has no `template` argument yet; milestone 3 adds it with `templates.py`. `RenderError` gained `detail`, since a run stores reason and detail in separate columns.
- Refused before anything is recorded against a subject (`ConfigError`): a video without a working encoder, a video with an odd `panel_px`, a `subject_uid` the run does not have, and a run directory inside a subject directory.
- What lies in the machine and not in a subject stops the phase with exit code 2 and is not recorded, so that the plain command does the work once the cause is gone. A failed row with the same hashes is not tried again without `--retry-failed`, and such a cause fails every subject alike. Two cases beyond the missing ffmpeg binary of the contract. The encoder: before the first batch of a render with video, ffmpeg encodes two 16 px frames into a temporary directory (about 20 ms here), which also catches a binary that starts and cannot encode. The media: an `OSError` from a render with `ENOSPC`, `EDQUOT` or `EROFS`, or with `EACCES` or `EPERM` on a path under `media/`, and a failure of ffmpeg whose text is that of the first three (ffmpeg writes the video itself and reports in words), end the call at that batch; nothing of the batch is recorded, and the renders of it that did succeed are found complete on disk by the next call. The inputs cannot cause these, because `render_subject` turns every error of reading them into a `RenderError`. Tried on tmpfs mounts as root: a full and a read-only run directory, `media/` on a full file system with and without video, an ffmpeg that exits with 1. Not covered: a disk that fills while ffmpeg writes and that ffmpeg reports in other words (the text was seen with the ffmpeg of imageio-ffmpeg on Linux only), and any other error of writing the output (`EIO`, a file where a directory should be), which are still recorded as `render failure` for the subject and need `--retry-failed`.
- A render that is complete on disk and has no row (a crash between the files and the row) is found complete by `render_subject`, which does nothing, and is then recorded.
- `render_status` says what a call would find now (done, failed, pending) without rendering; `surfcensus status` uses it. It was split off from `run_render` so that the two cannot disagree. `render_failures` names the subjects in the failed count with their reasons, and for an incomplete subject that has no `missing surface` row yet the detail that `run_render` will record.
- The check sample is drawn from the sorted `subject_uid`s of the done renders; the text file names the seed in its first line. It is written to `logs/` in a local run as well.

`Run` and the command line.

- `relocate` is a flag or the pseudonym of the dataset that moved (the contract had a flag and left the pseudonym to the command line). It replaces the root, and with it where the subjects lie under the root when the layout changed; the stored subject globs and field strength stay. A source given on opening whose root matches a stored one replaces that source's globs and field strength: from Python the source given is the truth. On the command line `--source` on an existing local run only says which source is meant, and `--subjects` and `--field-strength` change the stored values.
- `identity` of a local source is fixed when the run is created, not at the first inventory; the two differ only if the data moves in between.
- Sources are built when a phase first needs them, so `status` works on a run whose data is not mounted. A source that cannot be built stops `inventory` and `render` with exit code 2 before anything is recorded: a missing disk is not a property of its subjects. A `render` that finds nothing pending builds no source and reports its counts, so a finished run can be checked with the data unmounted; `Run.render` asks `render_pending` first, which plans the call a second time from the catalog.
- A run is created only in a new or empty directory, and by one process: `config.yaml` is written exclusively (a hard link from a temporary file, or an exclusive open on a file system without hard links), before the catalog. Of two processes that create a run in one directory at the same time, the one that comes second is refused with `invalid: ... already holds a run` and changes nothing. Before, it replaced the salt in `config.yaml` and was then refused by the catalog, which left a run that no command could open. In 40 races of two `inventory --source` commands after the change, one command was refused 7 times and no run was left unusable; a process that opens the run in the short time before its catalog is filled can still be refused with a message about the catalog, and loses nothing. A place where no run can be made (no permission, a read-only or full disk) is `ConfigError("invalid", "no run can be made in ...")`; a `config.yaml` left without a catalog by a full disk is a run whose catalog the next call makes.
- A run directory inside the subjects directory is refused, also for one subject directory as path, whose subjects directory is its parent. A run directory beside the subjects directory inside an fMRIPrep or derivatives folder is allowed.
- A `config` given on opening replaces the stored one when it is of the same run (mode and identity); this is how stored options are changed. `config.with_changes` validates a changed configuration as a whole. `from_config` takes `root` and `identity` from its caller when given, because a census run stores neither for a local source.
- A census run can be created from Python with the dataset key, with local sources or none, and opened without the key; its `inventory` needs the key. No command creates one before milestone 5.
- In a local run `Run.render(subjects=...)` accepts labels as well as `subject_uid`s.
- `--relocate [PSEUDONYM]` takes an optional value, which typer cannot declare; the command rewrites a bare `--relocate` before parsing.
- `status` prints done and failed for the inventory and no pending count, which the catalog cannot know without listing the source; for the render, pending is what `render` would do now. It always ends with 0. The render lines of `--failures` are the subjects in the failed count (review of milestone 2). Before, the list was every failed row of `renders`: after an inventory and before any render, `status` said `1 failed` for a subject without `lh.pial` and listed nothing, and a failure recorded for a subject that had since left the source, or that was pending again with other files or another configuration, was listed without being counted. Details of recorded failures still come from the private catalog.
- A phase command stopped by Ctrl-C ends with 130, not with the 1 that means failed units.
- An `OSError` or `sqlite3.OperationalError` that reaches a phase command (a catalog on a read-only disk, a disk that fills during a commit) is printed as one line `invalid: the run directory cannot be used: ...` with exit code 2, not as a traceback with exit code 1, which means failed units. Sources and renders turn their own errors into `SourceError` and failed units, so what arrives there is the run's. An inventory that changes nothing still writes the dataset row, so on a read-only run directory it stops this way, while `status` and a `render` with nothing to do work.
- Summary lines name subjects by label in a local run and by `subject_uid` in a census run.

Checked on real data (2026-11-12). Both subjects of the network tests, linked into one fMRIPrep layout in a scratch directory: `inventory` took under 0.1 s for the two (whole logs, local files) and gave FreeSurfer 6.0.1 and 7.3.2, 8 and 9 invocations over three logs, truncations 39:225 and 93:434, and 22:230 and 23:325; `render --jobs 2` took 9.0 s without video and `render --video` 17.5 s on one core; second calls did nothing; the source files had the same sizes and modification times afterwards. ## Open

O1. Package name. `surfcensus` is a placeholder. Decide with the paper team.

O2. When and how to reveal dataset identities. D10 settles the default (pseudonyms). Open: whether to reveal at all, and if so whether after notifying dataset authors, after publication, or on request only. Decide before phase 8.

O12. Licence for released ratings (CC0 proposed in `phases.md`). The code licence is settled in D17.
